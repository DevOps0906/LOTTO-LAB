# ADR-0005 운세·테마 번호는 기기에서 결정적으로 생성하고, 사주 프로필만 회원 동의 후 저장한다

- 상태: 채택
- 날짜: 2026-11-12

| 항목 | 내용 |
|---|---|
| 맥락 | 경쟁 서비스 다수가 생년월일·띠·별자리·꿈으로 "오늘의 번호"를 준다([benchmark.md#운세·테마 번호](../benchmark.md)). 재미 기능이지만 생년월일시는 개인정보이고, '맞춤 당첨' 류 표현은 금지 문구([01_PRD.md#6](../01_PRD.md))와 충돌한다. 게스트 사용(D6)과 기기 실행 원칙([ADR-0002](0002-engine-on-device.md))도 지켜야 한다. |
| 선택 | ① 공유 패키지 `packages/fortune-engine`(순수 TS, 기기 실행)이 입력→결정적 시드(입력+날짜, 같은 날 같은 결과)→`lotto-engine`으로 6개 생성(고정 번호 조합은 행운 숫자 테마만 — 착수 결정 ③). ② 테마 번호(비회원 가능): 별자리 12궁·띠 12지·생년월일·기념일 숫자·행운 숫자(=기존 고정 번호)·꿈 키워드(사전 매핑). 입력값은 서버로 보내지 않고 저장하지 않는다. ③ 사주 번호(회원 전용, P1): 생년월일·양/음력·태어난 시각(선택) → 천간지지·오행 → 같은 시드 규칙. 프로필은 동의 후 owner-only RLS 테이블 `fortune_profiles`에 저장, 계정 삭제 시 파기, 성별 등 불필요 항목 미수집. 로그인 세션 없으면 진입 차단+가입 유도. ④ 결과는 기존 generated 상태 그대로, 출처 `method`만 추가(random/condition/zodiac/birthday/dream/saju). ⑤ 모든 운세 화면에 "재미·참고용, 전통 상징 해석이며 당첨 확률과 무관" 고정 표기. |
| 대안 | ① 서버 계산: 생년월일시가 서버로 가고 오프라인 불가 → 기각. ② 사주도 게스트 허용·로컬 저장만: 기기 간 프로필 재사용 불가, 회원 가치 없음 → 기각(팀장 결정). ③ 매번 무작위: "오늘의 번호" 재현성이 없어 같은 입력에 결과가 계속 바뀜 → 기각. ④ AI 해몽: AI 키·위협 메모 필요 → P2로 미룸. |
| 결과 | 얻음: 오프라인·즉시 생성, 테마 입력값 서버 수집 0, 모바일·Windows 동일 결과. 잃음: 음양력 변환용 새 의존성(라이선스 확인 필요, GPL·AGPL 거부), 매핑 사전·엔진 수정은 앱 업데이트 필요, `fortune_profiles`라는 민감 데이터 저장 면 추가. 되돌리기: 엔진은 순수 함수라 교체 쉬움, 프로필 테이블은 삭제 마이그레이션으로 제거 가능(비용 낮음). |

- 범위(사용자 결정 2026-11-12): 로또 6/45와 연금복권 720+ 모두 적용(연금은 `pension-engine`으로 조·6자리 문자열 생성). 하루 1세트 — 시드가 입력+날짜라 같은 날 재생성해도 같은 결과(별도 카운터 없음).
- 착수 결정(2026-11-13 팀장, task-037 challenger 반영): ① method 매핑 — 별자리·띠 → `zodiac`, 생년월일·기념일 → `birthday`, 행운 숫자 → `condition`(고정 번호), 꿈 → `dream`, 사주 → `saju`(DB·스키마 변경 없음) ② 시드 = `fortune@1|<method>|<정규화 원본 입력>|<KST 날짜>|<game>|<기기 비밀값>` — 사주는 계산된 간지가 아니라 원본 입력(birth_date `YYYY-MM-DD`|calendar|leap|time 또는 없음)만, 꿈은 사전 ID 정렬, 문자열은 NFKC·trim. 기기 비밀값(설치 시 무작위 32바이트, 로컬 저장)으로 서버가 결과로 생일을 역산하지 못하게 함 — 대가로 기기 간 결과는 다를 수 있음(ADR 결과 '모바일·Windows 동일'을 이 항목으로 대체) ③ 하루 1세트 = 같은 날·같은 테마 입력·같은 복권이면 같은 결과, 로또 5게임·연금 기본 번호 1개×선택 조. 운세 번호에는 고정·제외를 섞지 않음(행운 숫자 테마만 고정 번호 방식) ④ engine_version = `fortune@1+lotto@1`/`fortune@1+pension@1` 조합, 하위 엔진 버전이 바뀌면 골든 벡터 실패 ⑤ 시드·정규화 입력은 결과·오류 detail·로그에 넣지 않음(테스트) ⑥ 띠는 직접 선택만(자동 판정 없음) ⑦ 간지·오행 표시(만세력·음양력 변환·절기·자시 학파)는 task-046으로 분리 — task-037은 새 의존성 없음 ⑧ 계층: `app-core → fortune-engine → (lotto-engine·pension-engine) → lottery-core → types`
- 사주 화면 결정(2026-11-13 팀장, task-041 challenger 반영): 프로필은 기기에 캐시하지 않고 매번 A-17 GET — 사주 번호는 온라인 필요(위 '오프라인·즉시 생성'의 예외). 고정 번호 옵션 없음(③), 로또·연금 모두. 생성 결과(번호·method만)는 다른 generated와 같이 기기에 남는다(생년월일 없음).
- 알려진 한계(2026-11-13 보안 리뷰): 시드는 FNV-1a 32비트 해시 4개로 xoshiro128** 상태를 만든다 — 비밀값 방어는 역산 비용을 올리는 수준이다. 강화가 필요하면 `fortune@2`에서 SHA-256 시드로 바꾼다. 비밀값 품질(CSPRNG 32바이트)은 엔진이 아니라 app-core가 보장한다(task-038).
- 확률 고지: 어떤 방식이든 각 번호의 당첨 확률은 같다. 운세 결과는 추천 번호(generated)일 뿐 구매·당첨 이력이 아니다(AGENTS.md 4장).
