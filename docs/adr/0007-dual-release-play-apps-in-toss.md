# ADR-0007 Google Play를 먼저 출시하고, 앱인토스는 토스 문의 답을 받은 뒤 별도 빌드로 추가한다

- 상태: 채택(2026-11-13 사용자: "구글 플레이 위주로") — 앱인토스는 보류, 어댑터 경계만 유지
- 날짜: 2026-11-13

| 항목 | 내용 |
|---|---|
| 맥락 | 사용자는 Google Play와 앱인토스(토스 미니앱) 동시 출시를 원한다(2026-11-13). 앱인토스 서비스 오픈 정책 3장 4)는 "speculative or lottery/betting content" 서비스를 등록 불가로 둔다 — 로또·연금복권 번호 생성·통계 앱은 반려 위험이 크다. 그 밖에 앱인토스는 로그인은 토스 로그인만, 광고는 앱인토스 광고만(외부 광고 네트워크 금지), 라이트 모드만, 앱마켓 링크 금지·외부 링크 제한, CSR/SSG WebView(SDK 3.x, `.ait` 100MB 이하), iOS는 쿠키 대신 토큰 인증, 토스에서 연결 해제 시 사용자 데이터 삭제·동의 이력 관리를 요구한다(출처: developers-apps-in-toss.toss.im 서비스 오픈 정책·서비스별 주의사항·비게임 체크리스트·FAQ, 2026-11-13 확인). |
| 선택 | ① Google Play(Capacitor) 기준으로 계속 개발한다. ② 사용자가 토스 파트너 창구에 "번호 생성·통계(구매 대행·판매 없음)" 가능 여부를 문의한다. 답을 받기 전에는 앱인토스 전용 작업을 만들지 않는다. ③ 대신 지금부터 플랫폼 차이가 나는 부분은 `packages/app-core` 인터페이스 + 앱별 어댑터로만 구현한다: 인증(`AuthClient` — Play는 Supabase 이메일, 앱인토스는 토스 로그인 → 서버 교환), 광고(슬롯 인터페이스 — Play는 AdMob, 앱인토스는 앱인토스 광고), 외부 링크·스토어 링크(플랫폼 플래그로 숨김), 테마(앱인토스 빌드는 라이트 고정), 보안 저장소(앱인토스는 SDK Storage가 앱 삭제 시 지워지므로 서버 보관 기준). ④ `packages/ui` 화면은 Capacitor·Supabase SDK를 직접 import하지 않는다(이미 지키는 규칙, 앱인토스 WebView 재사용 전제). |
| 대안 | ① 지금 둘 다 병행: 반려 시 토스 로그인·광고 연동이 전부 버려짐 → 기각. ② 앱인토스는 운세·사주만: 사용자 결정 보류(토스 답변에 따라 재검토). ③ 앱인토스 포기: 사용자가 원하지 않음 → 기각. |
| 결과 | 얻음: Play 일정 유지, 앱인토스 허용 시 어댑터 추가만으로 대응. 잃음: 어댑터 경계를 지키는 비용. 열린 결정: 토스 문의 결과, 허용 시 토스 로그인 사용자와 Supabase 계정 연결 방식(서버 교환 EF 필요 — 위험도 높음). |
