# 03 화면·UX — LOTTO LAB

> 근거: [브리프 D2·D6·D8·D10](PLAN_BRIEF.md#확정-결정), [원본 PRD 3·4·5·9장](../LOTTO_LAB_PRD.md). 지정된 docs/LOTTO_LAB_PRD.md는 없어 루트 원본을 참조했다. 형식은 ux-patterns 2절, 유형별 필수 구조는 같은 스킬 4절과 patterns.json을 따른다.
> 시안 직접 확인: [홈](../design/reference/m-home.png) → M-01, [로또](../design/reference/m-lotto.png) → M-02, [연금](../design/reference/m-pension.png) → M-03, [통계](../design/reference/m-stats.png) → M-04. 구성만 채택하며 이미지의 회차·날짜·번호·집계값은 실데이터로 전용하지 않는다. 벤치마크 채택 근거는 [benchmark.md](benchmark.md).
> 공통: 첫 실행 M-05/D-11 통과 전 앱 본문 접근 차단. 만 19세 미만·확인 거절은 종료 안내, 로그인으로 우회 불가. 게스트는 생성·로컬 저장·캐시 조회 가능, 로그인·동기화는 선택(P1). 모바일 탭은 홈·추천·통계·내번호; 추천 진입은 M-15, 상세에서 돌아오면 탭·필터·스크롤 복원.
> 반응형: ~767은 단일 열·하단 탭, 768~1199는 여유 열·Windows 아이콘 사이드바, 1200~는 Windows 라벨 사이드바·확장 표/차트. D-02/D-03은 Windows 두 구간에서 조건 좌측·결과 우측, 768~1199 아이콘 레일 사이드바 구간도 좌우 배치이며, 조건→결과 상하 순서는 모바일·웹 좁은 화면에만 쓴다. 창 최소 크기는 브리프 D10을 따른다. W-03/W-04도 좁으면 표를 카드로 바꾸며 권한·작업 순서는 유지한다.
> 색·서체·간격·반경·크기는 [토큰](../packages/design-tokens/tokens.css)의 --color-*·--font-*·--text-*·--spacing·--radius-*·--shadow-*만 사용. 신규 토큰은 디자이너 확인 대상이며 이 문서에서 값을 만들지 않는다. 안전 영역·키보드 초점·읽기 순서·입력 라벨·차트 대체 표를 제공하고 번호/상태는 색과 텍스트를 함께 쓴다.
> API 가정: 원본 PRD 9장 순서대로 A-01 최신 로또, A-02 최신 연금, A-03 회차 상세, A-04 로또 생성, A-05 연금 생성, A-06 통계, A-07 티켓 등록, A-08 내 번호, A-09 결과 대조, A-10 구독 조회. A-04/A-05는 미구현(D4, 서버 생성 없음)이라 화면 API 열에 두지 않고 생성은 기기 엔진이 실행하며, 조건 충돌은 HTTP 409가 아닌 엔진 오류 타입으로 받는다. A-10은 P2라 현재 화면에서 제외. 후속 계약 A-14 티켓 상태 변경(favorite→purchased), A-15 사전알림 신청, A-16 수집 재검증을 해당 화면에 연결한다. API의 —는 번호 계약 없음/로컬 처리이며 인증은 Supabase Auth. A-07/A-08/A-09는 로그인 클라우드 경로에만 적용한다. 후속 [API 명세](04_API.md#1-엔드포인트)의 A-11 수집 목록·A-12 승인·A-13 반려를 관리자 화면에 연결한다. 회차 목록은 [데이터 모델의 공개 읽기 RLS](05_DATA_MODEL.md#3-rls-정책)로 조회하며 단건 계약 A-03을 목록 API로 사용하지 않는다.
> 상태 의미: generated는 생성 이력, favorite는 명시 저장, purchased는 실물 구매를 사용자가 확인한 별도 기록. checked는 해당 purchased 기록의 대조 결과이며 미당첨·대기와 구분한다. 생성/저장만으로 구매·당첨 처리하지 않는다. 수동/QR 등록은 결제가 아니며 회차·번호 확인 후 확정한다. 금액은 정수 원, 연금 여섯 자리는 문자열(000719처럼 앞자리 0 보존).
> 공통 오류: 400은 해당 입력 옆 수정 안내, 생성 엔진 충돌 오류는 충돌 조건과 완화/게임 수 축소 제안, 503·오프라인은 마지막 검증 회차·출처·시각과 미갱신 배너. 캐시도 없으면 빈 상태로 안내하고 결과를 만들어 채우지 않는다. 당첨 판정 함수는 `lottery-core` 하나다: P0는 기기에서 공개 회차 데이터로 판정(캐시가 있는 회차만), P1 로그인 사용자는 A-09가 같은 함수로 서버 판정·이력 저장·푸시를 맡는다. 모든 결과는 공식 출처 링크·검증 시각, 모든 통계는 기간·표본 수·기준선·갱신 시각·출처·“미래 예측 아님”을 표시한다.
> 계약 확인 필요: 인증/재설정은 Supabase Auth를 사용한다. 구매일·정수 원 금액·원본 번호 연결·멱등 키는 `saved_tickets` 필드와 A-07/A-14로 처리한다. 동기화 병합·알림 이력/기기 등록은 API/데이터 명세 보완 대상이다. 관리자 목록은 A-11, 상세는 해당 목록 항목, 재검증은 A-16이며 재검증 통과 건만 A-12 승인 가능하다. 상세 재조회 계약은 미정이다. 없는 API ID를 만들지 않는다. 재시도 저장은 같은 멱등 키를 유지하고 중복 클릭을 잠근다. 웹은 브리프 Q2의 P1 가정, 관리자 쓰기는 서버 관리자 권한 검사 후 수행한다.
